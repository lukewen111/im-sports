## 一、需求背景与目标

### 1.1 需求背景

ChatScale 目前以客户主动咨询、客服接待及人工回聊为主要沟通方式，缺少面向历史客户的批量消息触达能力。当运营人员需要发送活动通知、业务公告或其他周期性消息时，无法通过统一的功能完成消息配置、定时推送和运行结果查看。

本次新增一级菜单【活动】，支持运营人员针对所选渠道内曾建立过会话、当前不存在未结束会话的客户，配置文本及图片消息，通过单次、周期性或立即运行的方式主动发送，并查看每次运行的执行结果。活动配置中的渠道支持在同一渠道类型内多选，发送者范围放开为租户内全部已启用成员；同时新增 SDK 活动分类，供集成方通过 SDK 接入的客户接收活动消息。

### 1.2 需求目标

- 支持网站小部件、Telegram、聊天页面三类渠道及 SDK 的历史客户主动触达。
- 支持单渠道类型内的渠道多选，以及租户内任意已启用成员作为发送者。
- 支持活动配置、定时执行、立即运行、启停及运行历史管理。
- 提供成功发送客户数、消息发送成功／失败数及任务运行状态，便于运营人员了解发送效果。
- 活动消息与正式会话接待业务隔离，不因批量推送产生新会话、干扰客服接待或影响报告指标。

## 三、功能详细说明

### 1．信息架构与功能范围

#### 1.1 菜单结构

在 ChatScale 左侧导航新增一级菜单【活动】（Campaigns），下设四个分类入口：

- 网站小部件
- Telegram
- 聊天页面
- SDK

点击【活动】进入模块，左侧展示上述分类，右侧展示当前分类的活动管理页面。右侧页面包含「活动」「运行历史」两个 Tab，并提供「创建活动」入口。

三类渠道共用相同的活动管理、配置及运行历史交互，数据按渠道类型独立展示。切换渠道类型时，右侧仅展示该类型的活动及运行历史。本期不改变系统登录后的原有默认进入页面。

SDK 分类仅在【活动】模块内新增，不进入【渠道】模块，不作为可配置的渠道类型。SDK 活动无渠道字段，其余配置项、执行方式、运行历史及失效规则与其他渠道类型一致；同一租户最多创建 1 个 SDK 活动。

#### 1.2 核心业务对象

| 对象 | 定义 |
|---|---|
| 活动 | 一组可保存的消息推送配置，包括名称、消息内容、渠道、发送者、触发时间及时区、启停状态。每个活动仅属于当前分类（网站小部件、Telegram、聊天页面或 SDK）；非 SDK 活动可绑定同一渠道类型下的一个或多个渠道实例，SDK 活动不含渠道。 |
| 渠道实例 | 渠道管理中创建的具体网站小部件、Telegram 或聊天页面，区别于左侧分类。SDK 分类下不存在渠道实例。 |
| 发送对象 | 本活动所选渠道内曾建立过正式会话、符合当前发送资格的客户；选择多个渠道时取各渠道候选客户的并集并按客户去重。SDK 活动的发送对象为通过 SDK 接入且符合发送资格的客户。 |
| 运行任务 | 活动每次由计划触发或立即运行所产生的一次独立发送任务。一个活动可对应多次运行任务。 |
| 活动消息 | 由活动任务产生的主动推送文本或图片消息，与正式会话业务消息独立。 |

活动启停状态描述配置是否继续按计划触发；运行状态描述某一次任务的执行结果。两者独立，不以运行历史的成功／失败直接替代活动状态。

#### 1.3 本期范围

| 本期支持 | 本期不支持 |
|---|---|
| 三类渠道及 SDK 的历史客户批量推送 | APP、Messenger 等其他来源的活动推送 |
| 同一渠道类型内渠道多选、单发送者、文本及单张图片 | 跨渠道类型选择渠道；自定义客户分群、手动选择客户、导入客户名单 |
| 单次、每天、每周、每月及立即运行 | 根据客户行为触发、复杂自动化工作流 |
| 活动创建、编辑、启停、删除及运行历史 | 活动专属客户退订功能、失败消息手动补发 |
| 成功发送客户数、消息发送结果及耗时 | 客户已读、点击、转化等营销效果统计 |

SDK 分类本期仅支持配置 1 个活动，具备与其他渠道类型一致的创建、编辑、启停、立即运行及运行历史能力；不提供 SDK 渠道管理、多活动并行或集成方侧的消息配置能力。

### 2．创建与编辑活动

#### 2.1 配置字段

点击当前分类页面中的「创建活动」，进入活动配置页。编辑活动时使用同一套表单，回显已保存的配置。页面字段及顺序如下：

| 配置项 | 控件 | 必填 | 默认值／规则 |
|---|---|---|---|
| 活动名称 | 单行输入框 | 是 | 内部活动标识，不作为消息发送给客户；当前分类内名称唯一，同一分类下不可重名，不同分类之间允许同名。 |
| 消息 | 多行文本输入框 | 条件必填 | 发送给客户的文本消息；文本和图片至少配置一项。 |
| 添加图片 | 图片上传 | 否 | 最多上传 1 张，支持预览、删除、更换。 |
| 选择渠道 | 下拉多选 | 是（SDK 无此字段） | 仅展示当前渠道类型下已启用的渠道名称；不限选择上限，至少选择 1 个；不允许选择其他渠道类型的渠道。SDK 活动不展示该字段。 |
| 发送者 | 下拉单选 | 是 | 候选范围为当前租户内全部已启用成员，范围见 2.3 节。 |
| 重复 | 下拉单选及联动选项 | 是 | 单次、每天、每周、每月。 |
| 时间 | 日期／时间选择器 | 是 | 根据重复频次确定是否选择年月日；时间精确到时、分。 |
| 时区 | 下拉单选 | 是 | 默认选中当前登录账号已配置的时区，如 UTC+00:00，可手动调整。 |
| 启用 | 开关 | 否 | 创建时默认关闭；开启并保存后，按配置的计划执行。 |

「重复」「时间」「时区」统一归入「触发时间」配置区域。

#### 2.2 消息配置

1. 文本与图片至少配置一项。空白文本不视为有效内容；二者均未配置时禁止保存。
2. 图片仅支持上传 1 张，不支持视频、文件等其他附件类型。文本字数、图片格式和大小沿用现有聊天消息发送规则，并同时满足当前渠道的限制；超出限制的配置不得保存。
3. 仅配置文本时发送一条文本消息；仅配置图片时发送一条图片消息；同时配置时的顺序及失败处理见 5.3 节。
4. 活动消息直接使用配置的原文，不应用客服个人的发送自动翻译设置，不为每名客户自动生成译文。
5. 活动名称只用于内部管理及运行历史识别，不拼接到对客消息中。编辑时名称唯一性校验排除当前活动自身。

#### 2.3 渠道与发送者

**渠道选择**

- 非 SDK 活动中，渠道为下拉多选且必填，至少选择 1 个渠道，不限制选择上限。候选项仅包含当前渠道类型下已启用的渠道实例，不允许选择其他渠道类型的渠道，也不允许通过一次活动混合多个渠道类型。
- 已停用或已删除的渠道不作为新配置的可选项；已保存活动引用的渠道失效时，按第 8 节处理。
- SDK 活动不展示「选择渠道」字段，保存时也不写入渠道数据。
- 切换活动分类或编辑活动时，活动所属分类不可变更；只能在同一渠道类型内调整所选渠道实例。

**发送者选择**

- 发送者为单选且必填，候选项为当前租户内全部已启用成员，不限定为所选渠道绑定的接待团队成员，也不再要求先选择渠道后才出现。
- 人类成员需处于启用状态；已停用、已删除的人类成员不提供选择。AI 成员可正常选择，包括其自动回复服务连接异常（连接异常）的 AI 成员；被标记为成员异常（不可用）的 AI 成员不提供选择。
- 在线、离线的有效成员均可选择。发送者仅作为活动指定的消息发送身份，不代表该成员必须在线接待，也不代表客户后续会话必然分配给该成员。
- 切换所选渠道时不再清空已选发送者，发送者选择独立于渠道。仅当发送者本身失效（成员被停用、删除或不可用）时，按第 8 节处理。
- 所选渠道不再决定发送者的可选范围，活动的发送范围仍由所选渠道及客户资格决定，不由发送者所属团队决定。
- 已保存活动的渠道或发送者发生失效、变更时，按第 8 节处理；配置失效的提示只说明失效数量，不逐一点名具体渠道。

#### 2.4 触发时间配置

| 重复频次 | 联动选项 | 时间控件 | 执行示例 |
|---|---|---|---|
| 单次 | 无 | 年月日＋时分 | 2026-12-01 10:00 |
| 每天 | 无 | 时分 | 每天 10:00 |
| 每周 | 周一至周日，多选，至少选择一天 | 时分 | 每周一、周三 10:00 |
| 每月 | 1日～31日，多选，至少选择一天 | 时分 | 每月1日、15日 10:00 |

1. 单次活动保存时，配置的触发时间必须晚于当前时刻（按所选时区判断）。编辑已过期单次活动时如需重新执行，应重新配置有效的未来时间或改为有效的周期性计划。
2. 每月所选日期在当月不存在时，跳过该日期，不提前到当月最后一天，也不延后到下个月。例如仅选择31日，11月不触发。
3. 多选重复日期时，所有选中日期共用一个时分及一个时区，不支持为每个日期配置不同时间。
4. 创建时默认时区取当前登录账号保存的时区，不取浏览器时区。活动保存后始终使用活动自身保存的时区执行；账号时区或设备时区后续变更不影响已有活动的计划时间。编辑时回显活动保存的时区。
5. 周期性活动不配置结束日期；启用后持续按计划触发，直到被暂停、删除或按第 8 节因配置失效而暂停。
6. 计划触发时间是任务开始执行的计划时间，而不是所有客户同时收到消息的时间。

#### 2.5 保存与编辑

- 创建或编辑时校验必填字段、名称唯一性、消息有效性、渠道数量与有效性、发送者有效性、计划时间及时区。配置无效时不允许保存，不生成新的发送任务。
- SDK 活动最多创建 1 个。已创建 1 个 SDK 活动后（无论其处于进行中、已暂停还是已过期状态），创建入口不可用并提示「SDK 最多创建 1 个活动」；直接访问创建页时不展示表单，提示已达上限并引导返回活动列表。删除现有 SDK 活动后释放名额；编辑现有 SDK 活动不占用新名额，也不会因保存产生第二个 SDK 活动。
- 创建时默认「启用」关闭。保存关闭状态的活动，仅生成活动配置，不自动发送消息；开启并保存后，等待符合条件的下一次计划时间。保存本身不等于「立即运行」。
- 编辑已启用活动时，保存有效配置后保留其启停状态，除非操作者主动修改启用选项或触发状态流转规则。
- 编辑不改变既有运行历史；运行期间编辑的生效边界见 4.4 节。
- 编辑因外部原因失效而自动暂停的活动时，必须恢复有效渠道与发送者配置，方可重新启用或立即运行。

### 3．活动列表

#### 3.1 筛选与排序

「活动」Tab 按当前分类（渠道类型或 SDK）展示已创建且未删除的活动，采用卡片形式。

| 筛选项 | 包含范围 |
|---|---|
| 全部 | 当前分类下所有未删除活动 |
| 进行中 | 已启用且计划尚未终止的活动 |
| 已暂停 | 未启用、手动暂停或因配置失效而暂停的活动（已过期除外） |
| 已过期 | 单次计划已消耗或已错过、不会再按原计划执行的活动 |

默认选择「全部」。各筛选项展示对应活动数量，例如「全部 (3)」「进行中 (2)」。三种活动状态互斥，全部数量等于进行中、已暂停及已过期数量之和。活动默认按创建时间倒序排列。

#### 3.2 活动卡片

| 区域 | 展示内容与交互 |
|---|---|
| 顶部左侧 | 活动名称，作为卡片大标题。 |
| 顶部右侧 | 启停开关，状态及可操作性见 4.1 节。 |
| 正文 | 有文本时显示消息文本，最多展示 2 行，超出省略，可悬浮查看完整文本；仅配置图片时，固定以文字「【图片】」展示。文本与图片同时配置时仅展示文本。 |
| 底部左侧 | 重复频次＋配置的计划时间，例如「每天 10:00」。时区仍在创建／编辑活动时配置并随活动保存，卡片不展示时区。 |
| 底部右侧 | 当前活动状态：进行中、已暂停或「已过期，不再执行」。卡片底部始终只显示活动状态；任务运行中不替换活动状态，也不额外展示「运行中」标识。 |
| 更多操作 | 位于卡片右上、启停开关左侧，鼠标悬浮在卡片上时出现；包含「立即运行」「编辑」「删除」三个选项，按第 4 节的规则控制可用性。 |

卡片不展示已添加图片数量、所选渠道数量及具体渠道名称，不将单次运行的成功／失败状态作为卡片活动状态。所选渠道或发送者失效时，仅在卡片失效提示中说明数量及原因类别（停用、删除或成员失效），不逐一点名具体渠道或成员，例如「所选渠道中有 1 个已停用」。

### 4．活动状态与运行控制

#### 4.1 活动状态及启停

| 活动状态 | 进入条件及含义 | 启停开关 |
|---|---|---|
| 进行中 | 活动已启用，存在有效的计划，等待触发或正在执行；单次计划已开始但任务尚未结束时仍可处于进行中。 | 开启，可手动暂停。 |
| 已暂停 | 创建时未启用、手动关闭，或因配置失效自动暂停；不产生后续定时发送任务。 | 关闭；配置有效时可重新启用。 |
| 已过期 | 单次活动已执行结束（成功或失败），或尚未运行而计划时间已过去；原单次计划不再执行。 | 关闭并置灰，不可直接启用。 |

状态变更规则：

1. 已暂停的有效活动手动启用后进入「进行中」，按下一次有效计划触发，不补发暂停期间错过的计划。
2. 进行中的活动手动关闭后进入「已暂停」。如果已经有任务开始执行，本次任务继续执行，不中断；仅停止后续计划。
3. 单次活动在一次有效运行结束后，无论运行结果成功或失败，均消耗该单次计划并进入「已过期」；即使运行期间关闭开关，原计划也不可再次执行。
4. 尚未启用或已暂停的单次活动，计划时间经过且未触发运行时，也进入「已过期」，不生成正常发送任务。
5. 已过期活动可以编辑。重新配置有效触发时间（或有效周期性计划）并保存后，恢复为「已暂停」，由操作者手动启用；历史记录保留。
6. 周期性活动单次运行成功或失败不改变其启停状态，后续仍依计划触发，配置失效例外见第 8 节。

#### 4.2 定时触发及错过计划

- 仅已启用且配置有效的活动按第 2.4 节的计划自动触发。每次有效计划触发产生独立运行任务，保存当次活动配置和执行记录。
- 系统异常导致已启用活动错过计划时间时，不自动补发；对应错过的计划记录为失败，不产生实际发送。单次活动因此过期；周期性活动继续等待后续计划。
- 未启用或手动暂停期间的计划不执行、不补发，也不生成失败运行记录。
- 同一活动同一时刻最多存在一个正在运行的任务。如果上次任务仍未完成且达到下一次计划时间，跳过本次新触发，不并行执行、不事后补发；该次被跳过的计划记为失败，与原运行任务独立。
- 已触发的任务不因操作者离开页面或退出登录而取消。

#### 4.3 立即运行

「立即运行」用于不等待预设时间，直接触发一次活动发送任务。点击后直接提交执行，无二次确认弹窗。

| 场景 | 处理规则 |
|---|---|
| 已启用的有效活动 | 支持立即运行。 |
| 已暂停但配置有效的活动 | 支持立即运行，不因手动执行自动开启周期性计划。 |
| 已过期活动 | 不支持；需先编辑为有效计划。 |
| 渠道或发送者已失效 | 不允许执行，需按第 8 节修正。 |
| 同一活动已有任务运行中 | 禁止再次立即运行，重复点击不产生新的并行任务。 |

立即运行使用当前已保存的有效配置，并遵循与定时触发一致的发送对象、发送规则、统计和历史保留规则。

- 单次活动提前立即运行时，消耗该单次计划，运行结束后进入「已过期」，原定计划不再执行；若任务尚未完成时到达原定时间，不再额外触发该计划。
- 周期性活动立即运行不改变其启停状态，也不改变原有下一次计划触发时间；如与正在执行任务冲突，遵循 4.2 节的并行限制。

#### 4.4 编辑及删除

- 支持编辑活动名称、消息、图片、渠道、发送者及触发配置。活动所属分类（渠道类型或 SDK）不可变更；非 SDK 活动只能在当前渠道类型内增减或更换渠道实例，SDK 活动始终不包含渠道。
- 活动运行期间允许编辑，当前运行使用任务开始时已确定的消息、渠道、发送者等配置，编辑结果仅对后续运行生效，不替换本次发送内容。渠道与发送者的实际失效仍按第 8 节处理。
- 已触发的单次计划不因编辑而恢复；若要再次定时执行，须以有效新计划重新配置。运行结束后按保存的有效新计划处理，不重复执行已消耗的旧计划。
- 删除活动需二次确认。正在运行的活动不允许删除，需等待本次运行结束后再删除。
- 删除后活动从卡片列表及活动状态数量中移除，后续不再触发；已产生的运行历史继续保留至其保留期限届满，不随活动删除而删除。

### 5．发送对象与消息发送

#### 5.1 发送对象范围

每次活动运行开始时，动态获取本活动所选渠道下曾建立过正式会话的历史客户，形成当次任务的候选发送名单；不以活动创建时的客户名单作为固定发送对象。选择多个渠道时，按客户 ID 合并各渠道的候选客户并去重，同一客户只作为 1 个发送对象。

发送资格必须同时满足以下条件：

1. 客户属于当前租户，并在本活动所选的任一渠道实例内建立过正式会话；不包含所选渠道之外的客户、仅访问过页面但从未建立会话的访客以及非正式测试记录。
2. 客户当前不存在任何未结束的正式会话，包括 AI 接待中、人工接待中及待分配。客户离线不是排除条件。
3. Telegram 客户还须符合第 8.3 节的新旧 Bot 身份及平台发送资格规则。

按客户 ID 去重。同一客户即使有多个所选渠道的历史会话，或在同一渠道内有多条历史会话，单次任务也只发送一次完整的活动内容（至多一条文本和一条图片）。不按渠道数量或历史会话数量重复发送。不自动合并姓名、邮箱或手机号相同的不同客户记录。

同一客户在多个所选渠道下都符合条件时，统一按该客户最近一次已结束正式会话所在的渠道发送本次活动消息；该客户的其他所选渠道不再重复发送。最近一次会话所在渠道已停用或删除时，按第 8 节处理，不降级到其他渠道补发。

SDK 活动的发送对象为通过 SDK 接入本租户、满足上述第 2 条资格且可由 SDK 触达的客户；SDK 无渠道维度，不做跨渠道去重。产品原型中 SDK 活动使用固定 3 个演示客户模拟运行统计与运行历史。

本期不提供客户分群、白名单、名单导入或退订配置。渠道自身的屏蔽、不可达等限制仍需遵守，不因本期不支持退订而绕过平台限制。

#### 5.2 运行期间的客户状态变化

- 每次运行开始时固定当次候选客户集合。运行开始后新增的历史客户不补入本次任务，下一次活动运行时重新计算。
- 在每条活动消息实际发送前（包括失败后重试前），再次校验该客户是否存在未结束会话。若存在，跳过其尚未发送的消息，不创建会话、不强行发送，也不将因该规则跳过的消息计入发送失败数。
- 文本成功后客户立即回复并产生新会话时，尚未发送的图片跳过；已成功发送的文本仍保留原统计结果。
- 已发送成功的消息不因客户随后发起会话而撤回；因未结束会话排除的客户不会在本次任务中因会话再次结束而补发被跳过的消息。

#### 5.3 发送顺序与自动重试

1. 单个客户同时配置文本和图片时，先完成文本消息的发送处理，再处理图片消息。文本和图片作为两条独立消息发送，不合并为图片附带文本的单条消息。
2. 文本最终发送失败时，仍继续处理图片消息，前提是客户仍符合发送资格。图片发送结果独立于文本发送结果。
3. 活动消息发送失败后支持自动重试。重试次数、间隔、限流及可重试错误类型由 RD 结合现有消息机制和渠道限制确定，本期不提供运营配置入口；对于平台明确禁止发送等不可恢复情况，无需无效重试。
4. 自动重试不得使已确认成功的同一条活动消息重复发送，也不按重试次数累计成功／失败消息数。最终发送失败的消息才计入失败数。
5. 活动批量发送遵循各渠道的平台限制及当前服务能力，允许分批完成；不能因触发时间已过去而将正在正常发送的任务误判为已结束。

#### 5.4 各渠道触达与成功判定

| 渠道类型 | 触达方式 | 单条消息发送成功判定 |
|---|---|---|
| 网站小部件 | 客户在线时可直接看到活动消息；离线时系统保存消息，待客户通过原有效身份再次访问时展示。 | 活动消息已成功保存并可供该客户查看。 |
| Telegram | 通过该渠道当前绑定的有效 Bot 向符合资格的历史客户发送。 | Telegram 发送接口确认本条消息发送成功。 |
| 聊天页面 | 客户在线时可直接看到活动消息；离线时系统保存消息，待客户通过原有效身份再次进入时展示。 | 活动消息已成功保存并可供该客户查看。 |
| SDK | 通过 SDK 向本租户已接入的客户下发活动消息，由集成方客户端展示。 | SDK 消息已成功下发至该客户。 |

- 活动消息统一以所选发送者身份发送，即「以所选成员身份发送」，展示该成员的身份信息；发送者不因执行活动获得接待归属或优先分配权。
- 网站小部件及聊天页面中，活动消息不依赖创建正式会话才能保存和展示；复用现有客户身份与离线消息触达能力的业务规则。
- 活动消息沿用现有 180 天消息可见期限，不新增活动专属消息有效期配置。客户原身份失效时不承诺通过新身份读取历史活动消息。
- 各渠道及 SDK 均不以客户实际打开页面、阅读消息或回复消息作为发送成功条件。「发送客户数」表示按上述业务口径成功触达的客户数，不是客户实际已读人数。

### 6．与现有会话及报告的关联

#### 6.1 会话业务隔离

活动消息是独立于正式会话的主动推送消息，不属于人工回聊创建会话的操作。

- 发送活动消息不创建正式会话，不产生待分配记录，不触发接管、转接或自动分配。
- 活动消息不在客服端「聊天」模块的会话列表、聊天窗口及历史消息中展示，不更新会话摘要、排序、未读数、客户业务消息最近活跃时间或消息提醒横幅。
- 不改变现有接待人，不重置会话自动结束或回复超时等计时，不触发 AI 自动回复。
- 本期不调整现有正式会话的创建、分配、接管、转接、结束和回聊等业务规则。

#### 6.2 客户回复活动消息

客户收到活动消息后主动发送业务消息，按正常客户进线处理：

| 客户回复时的情况 | 处理方式 |
|---|---|
| 当前存在未结束会话 | 进入原会话，沿用该会话的状态和接待规则；已有接待人继续负责，待分配仍按原待分配规则处理。 |
| 当前不存在未结束会话 | 创建新的正式会话，按现有规则优先分配给 AI 成员，AI 不可接待时分配给可接待的人工成员，无可用成员时进入待分配。 |

活动指定发送者不享有客户回复后的优先接待权，不因发送者是人类或 AI 成员改变自动分配规则。客户实际回复消息正常进入客服端聊天窗口及会话记录。

#### 6.3 AI 接待上下文

当客户在收到活动消息后进入正常接待流程且由 AI 成员接待时，系统应向 AI 提供该客户相关的、已成功发送且仍有效的活动消息作为必要的咨询上下文，以便 AI 理解客户针对活动的咨询。

活动消息仍不在客服端聊天窗口展示，也不作为新会话内由 AI 实际生成的回复；活动推送本身不触发 AI 接待或回复。上下文范围不得越过当前租户、渠道及客户身份，不应将未发送成功的活动内容当作客户已收到的内容。

#### 6.4 报告统计隔离

活动发送行为本身不纳入现有【报告 → 概览】或【报告 → 客服】的统计：不增加会话数、接待会话数、已回复会话数，不形成首次响应记录、聊天时间或效率分子，也不改变成员接受聊天状态及其时长。

客户回复后产生的正式会话与真实接待活动，仍依据原报告模块的统计口径纳入。活动的运行数据仅在【活动 → 运行历史】中查看，本期不增加报告模块的活动专题统计。

### 7．运行历史

#### 7.1 页面及筛选

「运行历史」Tab 以列表形式展示当前分类下所有活动已产生的运行任务，包括已删除活动保留期限内的运行记录。

| 筛选项 | 控件及规则 |
|---|---|
| 状态 | 单选，默认全部；选项为全部、运行中、成功、失败。 |
| 活动名称 | 关键词搜索，匹配运行时保存的活动名称，支持查询已删除活动的历史记录。 |

两个条件组合取交集，清空条件后恢复全部记录。列表按实际运行开始时间倒序排列；未实际开始的失败记录按对应计划触发时间参与排序。分页沿用现有 ChatScale 列表规则。

#### 7.2 列表字段

| 序号 | 表头 | 内容及展示规则 |
|---|---|---|
| 1 | 活动名称 | 本次运行触发时的活动名称快照。 |
| 2 | 状态 | 运行中、成功、失败；判定规则见 7.3 节。 |
| 3 | 发送客户数 | 本次运行中至少有一条活动消息发送成功的去重客户数，非计划发送客户数。 |
| 4 | 发送结果 | 按「成功 N / 失败 N」格式展示成功发送和最终发送失败的消息条数，保留斜杠，例如「成功 195 / 失败 5」。 |
| 5 | 运行时间 | 本次任务实际开始执行的时间，按当前登录账号保存的时区显示，日期格式沿用全站规则；未实际开始时显示「—」。 |
| 6 | 耗时 | 从任务实际开始到执行结束的时长；运行中显示已持续的时间，未实际开始时显示「—」。 |

数量以非负整数展示，使用英文逗号千分位，真实零值显示 0。运行历史不新增计划发送客户数、失败原因、失败客户明细或手动重发入口。

耗时按实际经过时间计算，以秒为最小展示单位，向下取整；超过24小时仍累计小时数，不转换为天。

| 耗时范围 | 格式 | 示例 |
|---|---|---|
| 不足1分钟 | 秒 s | 0s、35s |
| 满1分钟，不足1小时 | 分钟 m＋秒 s | 20m21s、1m0s |
| 满1小时 | 小时 h＋分钟 m＋秒 s | 1h10m10s、25h0m0s |

#### 7.3 运行状态判定

| 运行状态 | 业务定义 |
|---|---|
| 运行中 | 本次任务已触发并开始执行，仍有需要处理的发送任务或自动重试，尚未结束。 |
| 成功 | 本次任务正常执行结束，至少有一条消息发送成功；允许部分消息最终失败。没有符合发送条件的客户，或所有候选消息均因会话状态变化而被正常跳过且未发生发送失败时，也视为正常成功结束。 |
| 失败 | 本次任务未能正常执行或因异常而终止，或存在实际发送任务但最终没有任何一条消息成功且有发送失败记录。已启用活动因异常错过计划或因上一任务未结束而跳过新触发时，亦记录为失败。 |

「成功」是任务正常完成的业务结果，不表示所有客户均成功触达、所有消息均成功发送，也不表示客户已读。不新增「部分成功」状态；部分失败由「发送结果」反映。

没有符合条件客户时，发送客户数、成功消息数、失败消息数均为 0。任务异常终止时，已确认的成功及最终失败结果保留，不将未经处理的消息伪造为已成功或已失败的发送结果；没有实际发送的错过计划记录，其发送统计均为 0。

#### 7.4 发送客户数与发送结果统计

**发送客户数：**在同一次运行中，依据 5.4 节的渠道发送成功规则，至少有一条活动消息发送成功的客户数。以客户 ID 去重，每名客户最多计入 1 次。

**发送结果：**以消息为统计单位，分别累计本次运行中最终发送成功及最终发送失败的独立活动消息条数。一次文本发送及一次图片发送分别计为一条；同一条消息的自动重试不产生新的统计单位。因客户状态不满足条件而正常跳过的消息不计入成功或失败。

| 单个客户的发送结果 | 发送客户数 | 成功消息数 | 失败消息数 |
|---|---:|---:|---:|
| 仅配置文本，文本成功 | 1 | 1 | 0 |
| 仅配置图片，图片最终失败 | 0 | 0 | 1 |
| 文本、图片均成功 | 1 | 2 | 0 |
| 文本成功、图片最终失败 | 1 | 1 | 1 |
| 文本最终失败、图片成功 | 1 | 1 | 1 |
| 文本、图片均最终失败 | 0 | 0 | 2 |
| 文本成功，客户创建会话后图片被跳过 | 1 | 1 | 0 |
| 客户发送前已存在未结束会话，全部跳过 | 0 | 0 | 0 |

统计关系：

- 发送客户数 ≤ 成功消息数 ≤ 2 × 发送客户数；纯文本或纯图片活动中，两者相等。
- 单次运行的成功消息数和最终失败消息数之和不得超过该次候选客户数 × 每名客户配置的消息数量；跳过及未处理的消息不要求计入该和数。
- 同一客户在不同次活动运行中分别计算；不跨任务去重，也不将某次失败重试累计到另一任务中。

例如活动本次候选客户为 100 人，每人配置 1 条文本及 1 张图片。其中 95 人两条消息均成功，5 人仅文本成功且图片最终失败，则发送客户数为 100，发送结果为成功 195 条、失败 5 条，任务正常完成时状态为成功。

#### 7.5 实时更新与历史保留

- 运行中的任务实时展示发送客户数、成功／失败消息数及耗时；发送客户数随首条成功消息确认而增加，最终失败数在自动重试结束后更新。
- 页面能够反映任务由运行中转为成功或失败的结果，无需操作者手动刷新才看到最新状态。具体更新方式及频率由 RD 确定，本期不配置刷新间隔。
- 任务结束后，发送结果及耗时以最终统计记录为准，不随客户后续访问、已读、回复、活动修改等行为重新计算。
- 每次运行保留本次使用的活动配置及活动名称快照，修改活动名称、内容、渠道、发送者或时区不回写历史统计与运行名称。
- 删除活动后，既有运行记录仍可通过原分类及历史活动名称查询。运行历史自对应运行开始时间（未实际开始时自对应计划时间）起保留 365 天，不提供手动删除运行记录功能。活动配置删除及运行历史到期不应反向删除仍在有效期内的对客消息。

### 8．异常及关联对象变更

#### 8.1 渠道停用、删除与恢复

| 场景 | 活动配置处理 |
|---|---|
| 部分所选渠道被停用 | 自动暂停关联的未过期活动；保留其余有效渠道配置及运行历史，提示「所选渠道中有 N 个已停用」。 |
| 全部所选渠道被停用 | 自动暂停关联的未过期活动；保留原配置及运行历史，提示「所选渠道中有 N 个已停用」。 |
| 所选渠道重新启用 | 不自动恢复活动，由操作者确认配置有效后手动启用。 |
| 部分所选渠道被删除 | 自动暂停关联的未过期活动；保留其余渠道配置及历史，提示「所选渠道中有 N 个已删除」；需重新选择有效渠道后才能启用。 |
| 全部所选渠道被删除 | 自动暂停关联的未过期活动；保留历史，提示「所选渠道中有 N 个已删除」；需重新选择当前渠道类型下的有效渠道后才能启用。 |

失效提示只按停用、删除两类原因分别统计所选渠道数量，不展示具体渠道名称。同一活动同时存在停用和删除的渠道时，按原因分别计数并合并提示，例如「所选渠道中有 1 个已停用、1 个已删除」；同一渠道只计入其中一类。配置失效不影响已成功发送的消息及运行历史。

已过期活动保持已过期状态，不因渠道变更转为可执行活动。自动暂停不删除运行历史，不将已经成功发送的消息回滚。

#### 8.2 发送者失效

- 发送者不再要求属于所选渠道的接待团队，仅按成员自身的可用状态校验。活动指定的人类成员被停用或删除、AI 成员被删除或被标记为不可用时，关联的未过期活动自动暂停。修正配置后由操作者手动启用，不因成员恢复启用而自动恢复计划。
- 发送者所属团队变更、所选渠道变更不影响发送者有效性，不触发活动暂停。
- 发送者仅发生在线／离线切换，不影响活动配置或计划执行；AI 成员的自动回复服务连接异常（连接异常）不等同于其活动发送身份失效，仍可继续作为发送者。
- 成员昵称等展示信息变更不改变成员身份，仍按稳定成员 ID 识别。失效提示只说明发送者已失效，不逐一点名成员。

#### 8.3 Telegram 更换 Bot

区分同一 Bot 更新 Token 和将渠道更换为另一个 Bot：

| 场景 | 处理规则 |
|---|---|
| 同一 Bot 更新 Token | 活动不自动暂停，继续通过有效的新 Token 执行，原 Bot 历史客户发送范围不因更新 Token 而变化。 |
| 更换为不同 Bot | 活动不因 Bot 更换自动暂停，后续继续使用新 Bot 执行；仅向已与新 Bot 建立联系、属于该渠道且符合 5.1 节条件的历史客户发送。 |
| 客户仅与旧 Bot 建立过联系 | 不作为新 Bot 的合格发送对象，不使用旧 Bot 的历史联系关系直接视为新 Bot 具备主动发送资格。 |

新 Bot 客户资格随实际联系关系更新，在每次任务开始时重新确定。若没有符合条件的客户，按 7.3 节的零客户运行规则处理。Bot 更换本身不修改活动内容、计划或历史结果；现有会话及客户身份规则继续沿用原系统。

#### 8.4 任务执行中出现异常

- 任务开始及实际发送时均应满足当前渠道、客户及发送身份的有效性要求。手动暂停与普通编辑不打断当前有效运行；若渠道停用、删除或发送者失效导致发送资格不再成立，则不得继续向受影响客户发送剩余消息，并按实际任务异常及 7.3 节记录结果。
- 对正在运行的 Telegram 任务，不将已基于旧 Bot 确定的客户名单直接切换至新 Bot 批量发送；如更换使原发送配置不可继续执行，则结束受影响的本次任务，保留真实发送结果。下一次运行按 8.3 节使用新 Bot 重新确定发送对象，不自动补发。
- 渠道临时连接异常、消息发送超时等情况按第 5.3 节执行自动重试；单次任务异常不当然意味着周期性活动永久失效。
- 未触发、尚未确认结果或因规则跳过的消息，不因页面关闭、运行任务中断或请求异常而被错误计入发送成功。

#### 8.5 页面加载、空状态及通用显示

| 场景 | 页面处理 |
|---|---|
| 当前分类没有活动 | 展示活动空状态，保留创建入口；SDK 已达 1 个上限时创建入口禁用并提示上限。 |
| 状态筛选无匹配活动 | 保留筛选条件，展示无匹配结果。 |
| 当前分类没有运行记录或筛选无结果 | 保留表头及筛选区域，展示空状态。 |
| 活动配置已失效 | 按 8.1、8.2 在对应配置位置提示失效数量及原因，不点名具体渠道或成员，无法直接启用或运行。 |
| 加载或查询失败 | 提示失败并允许重试，不将未知统计结果显示为真实 0。 |
| 保存、立即运行或删除失败 | 提示失败，保留已确认的原配置或任务状态；不可将提交请求成功等同于发送成功。 |

活动模块界面文案沿用 ChatScale 现有工作台多语言机制。活动名称、消息内容、渠道名称、成员名称使用原始配置值，不自动翻译。运行时间按成员时区显示，活动卡片中的计划时间按活动保存时区显示，二者不混用。具体布局、控件样式、提示文案、空状态及加载表现以产品原型和现有系统交互规范为准。

### 9．角色权限与数据安全

#### 9.1 菜单权限

在「团队与角色 → 角色配置」中新增独立的【活动】一级菜单权限，仅设置一个功能权限项。四个分类入口（网站小部件、Telegram、聊天页面、SDK）及活动配置、启停、立即运行、编辑、删除、运行历史均由该菜单权限统一控制，不新增按钮级权限或独立的数据范围配置。

| 角色 | 权限规则 |
|---|---|
| Owner | 默认拥有活动权限，不可取消。 |
| 系统默认主管 | 默认不拥有新增活动权限，保持现有默认角色不可编辑的规则。 |
| 自定义管理员类型角色 | 可由 Owner 创建或编辑并授权活动权限。 |
| 普通成员类型（含系统默认客服） | 不提供活动权限授权项，不允许获得活动权限。 |

拥有活动权限后，可使用当前租户所有分类（三类渠道及 SDK）下的活动管理功能，选择当前租户的有效渠道和任意已启用成员，查看本租户全部活动及运行历史；不受本人或所属团队的聊天、客户、团队成员管理数据范围限制。

活动权限不依赖聊天、客户、渠道、团队或报告菜单权限，也不反向授予这些模块的访问或会话操作权限。按【报告】模块新增后的 14 项业务权限为基线，本次增加 1 项后共 15 项，原有权限及数据范围规则不变。若两个需求分批上线，权限项总数随实际已上线模块累加。

#### 9.2 权限校验与租户隔离

- 无活动权限时隐藏菜单，禁止直接访问活动路由及查询、创建、编辑、运行、启停、删除等操作；权限撤回后按系统既有权限机制即时生效，禁止继续通过已打开页面访问或发起操作。
- 活动、渠道、发送者、客户、运行记录及消息发送均限定在当前租户内，不得读取或操作其他租户的数据，不得向其他租户客户推送消息；不同部署环境之间不共享活动或运行记录。
- 配置、启用及执行时，应保证引用的渠道与发送者真实有效并满足对应租户、团队关系与发送规则，不能仅凭界面候选项放行无效配置。
- 已经合法触发并开始执行的任务属于租户活动任务，不因操作者离开页面、退出登录或后续丧失活动菜单权限而自动取消；后续管理操作仍需按最新权限校验。渠道、发送者及客户发送资格的失效处理仍按第 8 节及第 5 节执行。

| AT-19 | 同活动运行互斥 | 4.2、4.3 | 同一活动不会因重复提交或计划重叠产生并行发送任务；跳过的新触发按规定记录。 |
| AT-20 | 运行期间暂停 | 4.1、4.4 | 手动暂停后不再触发新计划，已开始且仍具备发送资格的任务正常完成。 |
| AT-21 | 运行期间编辑 | 4.4、7.5 | 已开始任务使用当次配置，新配置仅影响后续有效运行；既有历史配置及统计不被回写。 |
| AT-22 | 删除活动及历史保留 | 4.4、7.5 | 运行中的活动不可删除；合法删除后不再触发，但仍可查询保留期内的运行历史。 |
| AT-23 | 会话及客服端隔离 | 6.1 | 活动推送不新增会话、待分配、客服端聊天消息、未读或会话摘要变更，不改变接待人及会话计时。 |

| AT-25 | AI 上下文边界 | 6.3 | AI 接待能获取符合条件的相关活动上下文，活动本身不触发 AI 回复，且无跨客户或跨租户内容混入。 |
| AT-26 | 报告统计隔离 | 6.4 | 仅发送活动消息时，既有会话量及客服绩效统计不增加；真实接待活动仍按原口径统计。 |
| AT-27 | 渠道失效与恢复 | 8.1、8.4 | 部分或全部所选渠道停用、删除后相关活动被暂停且不再产生不合法发送，提示按原因只报数量、不点名渠道；恢复后不擅自重新启用，已成功结果及历史保留。 |
| AT-28 | 发送者失效 | 8.2、8.4 | 发送者被停用、删除或不可用时活动被暂停；所属团队变更、渠道变更、单纯在线状态变化及 AI 连接异常不导致错误暂停。 |
| AT-29 | Telegram Bot 变更 | 8.3、8.4 | 活动不会仅因 Bot 更换而自动暂停；实际使用正确 Bot 及相应合格客户范围，不向仅与旧 Bot 联系的客户误发。 |
| AT-30 | 发送客户数准确性 | 7.4 | 统计值与当次至少一条消息成功的去重客户集合数量完全一致，部分成功客户及重试不造成重复计数。 |
| AT-31 | 消息发送结果准确性 | 5.3、7.4 | 成功、最终失败条数与真实独立消息结果一致；未处理、跳过及中间重试不被重复或错误计入。 |
| AT-32 | 任务状态准确性 | 7.3 | 运行中、正常成功、部分消息失败、全部失败、零客户及异常终止等情形均按正文规则归类。 |
| AT-33 | 运行耗时准确性 | 7.2、7.5 | 耗时与实际任务起止时间一致；未实际开始的任务不产生虚假耗时，结束后数值不再持续增加。 |
| AT-34 | 历史数据一致性与期限 | 7.1、7.5 | 每次运行独立记录，实时累计与最终结果一致；活动修改、删除及客户后续行为不改写历史，记录按规定期限保留。 |
| AT-35 | 菜单授权范围 | 9.1 | 仅符合角色授权条件的成员获得活动功能；具备权限即可使用本租户活动，不额外获得其他菜单权限。 |
| AT-36 | 权限撤销及越权操作 | 9.2 | 无权或已撤权人员无法继续读取活动数据或发起管理操作；直接访问不能绕过权限。 |
| AT-37 | 租户及数据安全 | 5.1、6.3、9.2 | 活动配置、历史查询、发送对象及实际发送均保持当前租户和有效业务归属边界，无跨租户读取、修改或推送。 |
| AT-38 | 渠道多选口径 | 2.1、2.3、2.5 | 非 SDK 活动至少选择 1 个渠道且不限制上限，只能选择当前渠道类型下已启用的渠道，无法选择其他渠道类型或已停用、已删除的渠道。 |
| AT-39 | SDK 活动唯一性 | 1.1、2.5、8.5 | 同一租户最多存在 1 个 SDK 活动（含已过期）；创建入口在已有活动时禁用并提示上限，直接访问创建页被拦截；删除后释放名额，编辑不新增名额。 |
| AT-40 | SDK 活动配置一致性 | 1.1、2.1、2.3、5.1 | SDK 活动无渠道字段且不写入渠道数据，发送者、消息、重复、时间、时区及启停配置与其他渠道类型一致，可按立即运行并在运行历史中查看统计。 |
| AT-41 | 失效提示数量口径 | 2.3、3.2、8.1、8.2 | 渠道停用与删除按原因分别计数并提示数量，发送者失效单独提示；提示及卡片均不展示具体渠道或成员名称，计数与实际失效对象一致。 |

以上 41 项核心业务验收标准均须通过。本期不设置未确认的固定批量发送速度、渠道实际送达率或 AI 回答准确率门槛；平台限制导致的实际发送失败按真实结果统计，不以渠道外部失败本身等同于产品业务规则不通过。

3. 补充多渠道发送对象规则：各所选渠道候选客户取并集并按客户 ID 去重；同一客户在多个渠道均符合条件时，按最近一次已结束会话所在渠道发送，只发一次。
4. 发送者范围由「所选渠道接待团队成员」调整为「租户内全部已启用成员」：人类成员需启用，AI 成员可选（成员异常不可选，连接异常可选）；保持单选，切换渠道不再清空已选发送者。
5. 新增 SDK 活动分类：仅存在于【活动】模块，不进入【渠道】模块；无渠道字段，其余配置、执行及运行历史与其他渠道类型一致。
6. SDK 活动数量上限为 1 个：已过期活动仍占名额，删除后释放，编辑不新增名额；已有活动时创建入口禁用并提示「SDK 最多创建 1 个活动」，直接访问创建页时拦截并提示。
7. SDK 运行统计在产品原型中使用固定 3 个演示客户，用于展示发送客户数、成功／失败消息数及耗时。
8. 卡片与运行历史不展示渠道名称，仅在失效提示中展示失效数量；2.3 节改名为「渠道与发送者」，5.4 节明确活动消息「以所选成员身份发送」。
9. 8.1 节补充部分／全部渠道停用、删除的处理及计数口径；8.2 节删除发送者团队归属相关失效规则，改为仅按成员自身可用状态判断。
10. 验收标准同步更新 AT-01、AT-02、AT-03、AT-09、AT-11、AT-27、AT-28，并新增 AT-38～AT-41，合计 41 项。
